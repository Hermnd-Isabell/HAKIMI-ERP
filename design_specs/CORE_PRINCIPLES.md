# HAKIMI ERP 项目核心原则与设计规范 (Core Principles & Design Guidelines)

> **版本：** 1.0  
> **日期：** 2026-07-28  
> **地位：** **本项目最高优先级文档**。当代码实现、口头讨论或其他临时文档与本原则冲突时，一律以本原则为准。

---

## 1. 设计参考与权威来源 (Sources of Truth)

本项目的设计严格基于以下资产，按优先级排序如下：

1.  **最高准则：** `refer_docs/系统设计报告.docx` (包含 UI 原型与 API 契约)
2.  **数据准则：** `refer_docs/第二阶段-逻辑模型设计报告(1).docx` (包含实体关系与数据字典)
3.  **交互准则：** `refer_docs/终端适配与通用交互规则.txt` (包含配色、校验与适配逻辑)
4.  **外部标准：** SAP S/4HANA SD (Sales and Distribution) 业务流程标准。

## 2. 核心设计原则 (Core Principles)

### 2.1 命名一致性 (Naming Consistency)
*   **术语标准：** 内部技术实现、数据库、API 一律使用 **`Business Partner` (BP)**；UI 界面、用户文档一律使用 **`Customer` (客户)**。
*   **代码风格：** 
    *   后端/API/数据库：`snake_case` (如 `bp_id`, `sales_order_id`)。
    *   前端代码：`camelCase` (如 `bpId`, `salesOrderId`)。
    *   常量：`SCREAMING_SNAKE_CASE` (如 `STATUS_CLOSED`)。

### 2.2 多人协作冲突规避 (Collision Avoidance)
*   **原子性开发：** 每个人应在独立的 Feature 分支开发。禁止在未沟通情况下修改他人负责模块的核心逻辑。
*   **契约先行：** 在修改任何已定义的 API 契约或数据库 Schema 之前，必须先在 `refer_docs` 基础上发起 RFC (Request for Comments) 并获得确认，严禁“先斩后奏”。
*   **代码保护：** 严格遵循 `Single Responsibility Principle` (单一职责原则)。如果一个函数或类变得过于庞大，必须拆分，以减少多人同时编辑同一位置的概率。

### 2.3 零冗余与极致简洁 (Minimalism & Clean Code)
*   **拒绝历史遗留：** 严禁提交任何注释掉的代码段、过期逻辑或试验性质的无用文件。
*   **高标准重构：** 发现重复代码 (DRY) 必须第一时间重构为公共组件或工具类。
*   **删除即贡献：** 鼓励删除不再使用的逻辑。冗余代码是系统的负债，而非资产。

### 2.4 状态机约束 (State Machine Integrity)
*   **不可逆性：** 遵循 O2C 业务逻辑，单据一旦进入 `CLOSED` 或 `CLEARED` 状态，严禁通过任何 API 进行非审计式的修改。
*   **转换一致性：** 单据间的转换（如 Quotation -> Order）必须由后端服务层原子性完成，包括源单据的关闭和目标单据的创建。

---

## 3. 开发红线 (Hard Redlines - 违者必究)

1.  **禁止绕过校验：** 严禁为了开发方便在前端或后端跳过 `refer_docs` 规定的三级校验逻辑。
2.  **禁止硬编码：** 严禁在代码中直接硬编码色值、错误码字符串或业务配置。必须引用全局常量定义。
3.  **禁止物理删除：** 业务单据（D3/D4/D5）一律采用状态位管理（如 `status = 'CANCELLED'`），严禁执行 `DELETE` 操作。
4.  **禁止非契约变更：** 严禁修改已联调通过的 API 返回结构，即使是添加一个字段，也必须同步更新 API 文档。

---

## 4. 协作机制

*   **冲突决策：** 当两名开发者对某一设计点产生分歧时，应追溯至 SAP SD 标准业务实践。若仍无法解决，由项目首席架构师（或当前对话的发起者）裁定。
*   **文档同步：** 任何代码层面的结构性变更，必须在 24 小时内同步更新到 `refer_docs` 的 MD 版本中。
