第一部分 系统原型报告
第1章 引言
1.1 编写目的
本文档基于上一阶段完成的《逻辑模型设计报告》，将系统的数据流、实体关系与业务规则转化为可视化的界面原型与交互规范。作为面向开发团队的交接文档，本文档旨在：（1）为前端开发人员提供统一的页面布局、配色与组件规范；（2）为后端开发人员明确各页面的数据接口、字段约束与状态流转；（3）保证后续开发工作与逻辑模型设计的一致性，避免需求漂移。
1.2 范围
本报告覆盖简化版 SAP SD 系统的核心界面原型，包括：
（1）首页（Home）：系统入口与驾驶舱概览；
（2）客户管理（Customer Management）：以“创建业务伙伴（Create Business Partner）”为代表的多字段表单页；
（3）销售管理（Sales Management）：以“创建报价单行项目（Create Quotation: Item Data）”为代表的表格式复杂录入页；
（4）发货管理（Delivery Management）：交货状态监控列表与交货详情页；
（5）财务管理（Financial Management）：未清应收账款列表与应收详情页；
（6）通用组件：F4 搜索帮助弹窗、成功提示弹窗等全局组件。
1.3 参考文档
本报告编制过程中主要参考以下文档：
（1）《简化版 SAP SD 系统逻辑模型设计报告》（2026年7月19日）
（2）《终端适配与通用交互统一规则》（项目组内部规范）
（3）本报告配套设计图（共8张）
（4）主题色选色色卡
第2章 设计概述
2.1 设计理念
本系统采用 “专业、克制、自然” 的设计哲学。ERP 系统的核心是效率与准确性，因此界面设计遵循以下原则：
（1）信息密度优先：在有限屏幕空间内呈现更多有效字段，减少页面跳转；
（2）状态可视化：通过颜色、标签、进度条将业务状态（如发货进度、收款进度）直观呈现；
（3）操作可预期：同一类操作在不同模块中保持一致的入口、反馈与快捷键；
（4）视觉降噪：使用低饱和度的自然色系，降低长时间操作的视觉疲劳。
2.2 色彩系统
系统采用四色自然配色方案，灵感来源于“苔藓与纸张”的质感，呼应新拟态（Neumorphism）的柔和光影：

（3）首页新拟态卡片：使用 #FBFADA 与 #ADBC9F 的明暗阴影组合，营造凸起/凹陷的物理质感。

2.3 字体与排版
字体族：系统无衬线字体栈 Inter, -apple-system, "Segoe UI", sans-serif，数字与金额使用等宽字体 SF Mono, Consolas, monospace 以保证对齐；
字号层级：
（1）页面标题：20px，加粗，#12372A
（2）区块标题（Section Title）：14px，加粗，#436850，常带图标前缀
（3）表单标签：13px，常规，#12372A
（4）表格正文：13px，常规
（5）辅助文字：12px，#12372A 60%透明度
2.4 布局框架
系统采用经典的 “左侧固定导航 + 右侧自适应内容” 布局：
（1）左侧导航栏：固定宽度 220px，背景色 #12372A，可折叠；包含 Logo、菜单树、底部机器人助手入口；
（2）顶部操作栏：高度 56px，包含面包屑/页面标题、全局搜索、通知铃铛、帮助、用户头像与角色切换；
（3）内容区：背景 #FBFADA，最小宽度 1280px（低于此宽度出现横向滚动），在 1920px 以上时内容区最大宽度 1400px 并居中；
（4）页脚：极简版权信息，高度 40px。

交互说明：

与逻辑模型映射：

（2）信息卡片区：Delivery Date、Planned GI Date、Carrier、Delivered/Total；

第5章 通用交互与前端规范
5.1 表单校验规则
基于《终端适配与通用交互统一规则》，系统采用三级校验机制：
（1）失焦校验（Blur Validation）：
字段失去焦点时触发格式校验（邮箱、邮编、编号规则）；
仅在字段被修改后触发，避免打开编辑页满屏红框；
异步校验（如编号唯一性）需带 500ms 防抖，显示“校验中…”状态。
（2）提交校验（Submit Validation）：
必填项、跨字段逻辑（如结束日期 ≥ 开始日期）在点击保存时统一触发；
错误汇总并自动滚动定位到第一个错误字段。
（3）提示样式：
字段下方固定预留 20px 错误提示区，避免布局抖动；
错误文案格式：[字段名称] + [具体错误]，如 “Postal Code format is invalid”。
5.2 表格交互规范
固定列：首列（勾选/编号）与尾列（操作）固定，中间列横向滚动；
列宽：日期/状态列最小 100px，名称/备注列自适应或最小 200px；
低分辨率适配（1366px）：默认展示核心列，非核心列通过“列展示设置”由用户自定义；
分页器：固定在内容区底部，左侧显示总条数，中间页码，右侧每页条数选择器；
跨页选择：仅记住当前页选中项，翻页清空，提供“选择全部 N 项”按钮；
无数据状态：骨架屏首次加载，空状态显示插画 + “暂无数据” + 引导按钮。

整套设计覆盖 SD 端到端业务流程的单据流（Document Flow）：
询价 → 报价 → 销售订单 → 交货 → 发货过账 → 发票 → 收款 / 应收清账
所有表采用 InnoDB 引擎 + utf8mb4 字符集，五个子库部署在同一 MySQL 实例内，跨子库全部采用物理外键直接关联，形成端到端的参照完整性闭环。
第2章 总体设计原则
1. 抬头–行项目双层结构：所有业务单据均拆分为抬头表（Header）与行项目表（Item），符合第三范式，避免一张单据多行产品造成的重复组问题。
2. 主数据与单据分离：客户（D1）、物料（D2）作为主数据独立建表，被各单据以物理外键引用，保证主数据一处维护、处处一致。
3. 业务单号作主键：主键统一采用 VARCHAR(20) 业务凭证号；客户销售/财务视图采用符合 SAP 习惯的复合主键（按销售区域、按公司代码）。
4. 行号唯一约束：行项目表在主键之外另设 (单据号, item_no) 唯一键，保证同一单据内行号不重复，符合 SAP 行项目编号（10、20、30…）习惯。
5. 单据流可溯源：下游单据保存上游单据号作为外键（quotation.inquiry_id、sales_order.quotation_id、delivery_item.so_item_id、invoice.delivery_id），完整还原业务链条。
6. 删除策略分级：抬头→行项目使用 ON DELETE CASCADE；主数据引用、财务凭证与物流过账使用 ON DELETE RESTRICT，防止误删有业务依赖的记录。
第3章 D1 客户主数据设计
D1 采用 SAP Business Partner（业务伙伴）理念：同一客户主体只存一条主记录，其承担的不同角色（售达方/送达方/付款方）、不同销售区域视图、不同公司代码视图分别扩展为从表，避免客户基础信息冗余。
3.1 business_partner（业务伙伴主记录）
主键：bp_id
关键属性：bp_type（伙伴类型）、bp_role（角色：售达方/送达方/付款方）、bp_name、国家/城市/区县/街道/门牌/邮编等地址字段、language、time_zone、transportation_zone（运输区域，供 D4 线路调度）、telephone / mobile_phone / fax / email、status（默认 ACTIVE）、block_reason（冻结原因）、created_time / last_changed_time（自动维护时间戳）、data_source、print_format 等。
设计说明：created_time 默认 CURRENT_TIMESTAMP，last_changed_time 带 ON UPDATE CURRENT_TIMESTAMP，由数据库自动维护审计时间。
3.2 customer_sales_data（客户销售区域数据）
主键：(bp_id, sales_org, distribution_channel, division) 复合主键——同一客户在每个销售区域下各有一条视图数据，与 SAP 客户主记录销售视图一致。
外键：bp_id → business_partner(bp_id)，ON DELETE RESTRICT
关键属性：sales_office、sales_group、sales_district、currency、price_group、customer_pricing_procedure（定价过程）、delivery_priority（交货优先级）、shipping_condition（装运条件）、delivering_plant、max_partial_deliveries、incoterms、account_assignment_group（科目分配组，供 D5 财务过账）、tax_classification（税分类）。
3.3 customer_finance_data（客户公司代码财务数据）
主键：(bp_id, company_code) 复合主键——同一客户在每个公司代码下各有一条财务视图。
外键：bp_id → business_partner(bp_id)，ON DELETE RESTRICT
关键属性：reconciliation_account（统驭科目）、sort_key、payment_terms（付款条件）、银行信息（bank_account_name、bank_country、bank_key、bank_account、iban、bank_account_status）、支付卡信息（card_type、card_number、preferred_card、card_status）。
3.4 contact（联系人）
主键：contact_id
外键：bp_id → business_partner(bp_id)，ON DELETE RESTRICT（一个客户 1 : n 个联系人）
关键属性：contact_type / contact_role、姓名（first_name / last_name / birth_name）、地址字段、personal_phone、wechat、linkedin、gender、marital_status、nationality、birthday、occupation、department、position 等。
3.5 bp_relationship（业务伙伴关系）
主键：relation_id
外键：bp_from / bp_to → business_partner(bp_id)，双外键自引用，表达伙伴之间的有向关系（如"集团-子公司"、"雇主-雇员"），均为 RESTRICT。
关键属性：relationship_type（关系类型）、valid_from / valid_to（关系有效期）。
3.6 D1 关系结构小结
business_partner ──1:n── customer_sales_data（按销售区域）
                 ──1:n── customer_finance_data（按公司代码）
                 ──1:n── contact
                 ──1:n── bp_relationship（bp_from / bp_to 双外键自引用）
第4章 D2 物料主数据设计
4.1 material（物料主记录）
主键：material_id
关键属性：material_name（NOT NULL）、description、base_unit（基本计量单位，NOT NULL）、standard_price（标准价格，DECIMAL(15,2)）、weight / volume（重量/体积，DECIMAL(15,3)）、search_term。
设计说明：material 被 D3、D4、D5 的全部行项目表以 ON DELETE RESTRICT 引用，是全库被引用最多的主数据表；已发生业务的物料禁止删除，只能通过状态管理停用。
第5章 D3 业务单据数据库设计
5.1 inquiry（询价单抬头）
记录客户询价的核心信息，是销售流程的起点单据。
主键：inquiry_id
外键：customer_id / sold_to_party / ship_to_party → business_partner(bp_id)（客户三方：客户·主、售达方、送达方）
关键属性：inquiry_type、status、created_time / created_by、customer_reference（客户参考号）、sales_area / sales_org / distribution_channel / division（销售范围）、requested_delivery_date、valid_from / valid_to、pricing_date、currency、delivering_plant、incoterms、delivery_location、payment_terms、max_partial_deliveries、net_value、inquiry_address 等。
设计说明：在 ER 原图基础上补充了客户三方外键，解决原图抬头表无法定位客户主数据的问题。
5.2 inquiry_item（询价单行项目）
主键：inquiry_item_id；唯一键 (inquiry_id, item_no)
外键：inquiry_id → inquiry（CASCADE，1 : n）；material_id → material（RESTRICT）
关键属性：order_quantity、sales_unit、expected_order_value、unit_price、discount、net_price、item_description。
5.3 quotation（报价单抬头）
主键：quotation_id
外键：inquiry_id → inquiry（单据流，可空）；customer_id / sold_to_party / ship_to_party → business_partner
关键属性：与询价单结构基本对应（quotation_type、valid_from / valid_to 报价有效期、net_value、quotation_address 等），便于从询价单复制生成。
5.4 quotation_item（报价单行项目）
主键：quotation_item_id；唯一键 (quotation_id, item_no)
外键：quotation_id → quotation（CASCADE）；material_id → material（RESTRICT）
属性结构与 inquiry_item 一致，支持询价→报价的无缝参照。
5.5 sales_order（销售订单抬头）
SD 模块的核心单据，是后续交货（D4）与开票（D5）的直接依据。
主键：sales_order_id
外键：quotation_id → quotation（单据流，可空）；customer_id / sold_to_party / ship_to_party → business_partner
关键属性：order_type、reference_type（参照类型信息列：询价/报价/直接）、customer_reference（客户 PO 号）、requested_delivery_date、pricing_date、payment_terms、incoterms、delivering_plant、net_value、status 等。
5.6 sales_order_item（销售订单行项目）
主键：so_item_id；唯一键 (sales_order_id, item_no)
外键：sales_order_id → sales_order（CASCADE）；material_id → material（RESTRICT）
关键属性：通用价格字段之外，增加 availability_status（ATP 可用性检查状态）与 confirmed_quantity（确认数量）；同时作为 D4 delivery_item.so_item_id 的被引用方，衔接物流交货环节。
5.7 D3 关系结构小结
inquiry ──1:n── inquiry_item ──n:1── material
   │1
   │n（可空，单据流）
quotation ──1:n── quotation_item ──n:1── material
   │1
   │n（可空，单据流）
sales_order ──1:n── sales_order_item ──n:1── material
   │
   └──（customer_id / sold_to_party / ship_to_party）──n:1── business_partner
第6章 D4 物流数据库设计
6.1 delivery（交货单抬头）
主键：delivery_id
外键：ship_to_party → business_partner(bp_id)，RESTRICT（收货方）
关键属性：delivery_type / delivery_status（NOT NULL）、planned_delivery_date（计划交货日）、planned_gi_date / actual_gi_date（计划/实际发货过账日）、picking_date（拣配日期）、shipping_point（装运点）。
6.2 delivery_item（交货单行项目）
主键：delivery_item_id；唯一键 (delivery_id, item_no)
外键：delivery_id → delivery（CASCADE，1 : n）；material_id → material（RESTRICT）；so_item_id → sales_order_item(so_item_id)，单据流外键，可空，记录来源销售订单行。
关键属性：delivery_quantity（交货数量）、sales_unit、item_description。
设计说明：so_item_id 直接引用到"订单行"而非订单抬头，支持一张订单分多次部分交货（与 max_partial_deliveries 配合），是 D3→D4 的关键衔接点。
6.3 goods_issue（发货过账）
主键：goods_issue_id
外键：delivery_item_id → delivery_item（RESTRICT，按交货行进行过账）
关键属性：goods_issue_time（过账时间，NOT NULL）、actual_quantity（实际发货数量）、posting_date（过账日期，NOT NULL）、warehouse（仓库）。
设计说明：发货过账是库存扣减与物权转移的确认点，actual_gi_date 回写到交货抬头后，物流环节完成，进入 D5 开票。
6.4 D4 关系结构小结
sales_order_item ──1:n── delivery_item ──n:1── material
                        │n        └──1:n── goods_issue
delivery ──1:n─────────┘
   │
   └── ship_to_party ──n:1── business_partner
第7章 D5 财务数据库设计
7.1 invoice（发票抬头）
销售开票凭证，是物流交货之后的财务确认环节。
主键：invoice_id
外键：delivery_id → delivery（开票以交货单为参照，与 SAP"参照交货开票"一致）；sales_order_id → sales_order（信息列，保留订单来源）；sold_to_party / payer → business_partner（售达方与付款方，允许不同，如集团代付）。
关键属性：billing_type、invoice_date / billing_date、销售范围三要素、shipping_point、destination_country、currency、total_amount、status（未清/部分清/已清/已冲销）。
7.2 invoice_item（发票行项目）
主键：invoice_item_id；唯一键 (invoice_id, item_no)
外键：invoice_id → invoice（CASCADE）；material_id → material（RESTRICT）
关键属性：quantity、unit_price、discount、net_price，并特有 tax_amount（税额）字段，满足财务开票含税核算需求。
7.3 open_account_receivable（未清应收账款）
发票开立后生成的未清应收记录，用于账龄与催款管理。
主键：open_ar_id
外键：invoice_id → invoice，RESTRICT（1 : 1）
关键属性：receivable_amount（应收金额）、received_amount（已收金额，随收款逐次更新）、created_time、due_date（到期日）、status（未清/部分清/逾期）。
7.4 closed_account_receivable（已清应收账款）
发票全额收款后的已清应收档案记录，与未清表结构对应。
主键：closed_ar_id
外键：invoice_id → invoice，RESTRICT
关键属性：receivable_amount、received_amount（实收金额）、created_time、closed_time（清账时间，本表特有）。
设计说明：原 ER 图中本表缺少与 Invoice 的关联属性，物理设计中已补充 invoice_id 外键（SQL 注释"原图缺失，已补"）。
7.5 receipt（收款单）
记录每一次实际收款动作，一张发票可分多次收款。
主键：receipt_id
外键：invoice_id → invoice（1 : n）；payer → business_partner（实际付款方）
关键属性：receipt_date、receipt_amount、payment_method（现金/银行转账/汇票等）、currency、reference_no（银行流水号/票据号）。
7.6 D5 关系结构小结
delivery ──1:n── invoice ──1:n── invoice_item ──n:1── material
sales_order ──1:n──┘   │
                       ├──1:1── open_account_receivable
                       ├──1:1── closed_account_receivable
                       └──1:n── receipt ──n:1── business_partner(payer)

第10章 总结
1. 全库 20 张物理表全部满足第三范式：主数据按视图拆分、单据按抬头–行项目拆分，消除重复组与传递依赖。
2. 通过 4 个单据流外键完整还原"询价→报价→订单→交货→发票"的 SD 业务链条，且均为可空设计，兼容跳步业务。
3. 五个子库在同一实例内实现全物理外键贯通：单据抬头引用客户三方、行项目引用物料、交货行引用订单行、发票引用交货单与付款方，形成端到端参照完整性闭环。
4. 客户主数据采用 SAP Business Partner 模式（一条主记录 + 销售区域视图 + 公司代码视图 + 联系人 + 伙伴关系），财务侧采用"未清应收 → 收款 → 已清应收"三表配合，高度贴近真实 SAP SD/FI 设计。
5. 对原 ER 图的缺失做了两处合理补充：D3 抬头补充客户三方外键、D5 已清应收表补充 invoice_id 外键，并在 SQL 中留有注释备查。
